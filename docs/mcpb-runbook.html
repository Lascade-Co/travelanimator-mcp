Travel Animator MCPB

Shipping travel-animator as an MCP Bundle for Claude Desktop, using the uv server type — dependencies declared, not vendored, so the bundle stays about 100 KB instead of carrying an 86 MB wheel.

  • 0.4 manifest version
  • uv server type
  • ~100 KB bundle
  • 3.12+ python
  • 4 platform wheels
  • 38 tools, annotated

00

Send the email before you submit

Blocking

Three policy questions now, none answered. The first two were raised before any of this was built; 1.1.0 added the third, and it is the sharpest.

Blocking gates
  1. Financial transactions. 1.1.0 ships buy_credits. The policy bars software that "transfers money, cryptocurrency, or other financial assets, or executes financial transactions on behalf of users," and one of the seven mandatory acknowledgments covers exactly this. The tool returns a Stripe checkout link and charges nothing — its own description tells the assistant to show the link and states that nothing is bought until the user finishes Stripe's page — so a strict reading puts it outside the prohibition. That reading needs confirming, not assuming.
  2. The open-source clause. Does the non-waivable MCPB clause apply to a bundle whose only contents are a manifest and a dependency declaration, where the host fetches the wheel from PyPI?
  3. AI media. Confirm deterministic rendering — map tiles and a fixed 3D catalogue, no generative model — sits outside "generate video via AI models."

Email mcp-review@anthropic.com. A rejection on financial grounds costs a full review cycle; asking first costs a reply.

06

Exclusions and icon

Done

mcpb/.mcpbignore

.venv/
server/lib/
server/venv/
__pycache__/
uv.lock

The spec is explicit that uv bundles must not ship server/lib/ or server/venv/. uv.lock is excluded too, for a reason worth stating: running the server locally writes one, and packing it would freeze every transitive dependency at the moment you happened to test — blocking security patches until you cut and resubmit a new bundle. The wheel itself is already pinned exactly, so the lock buys nothing the pin does not. The reference hello-world-uv example omits it as well.

09

Privacy policy

Live, retention unstated
Rejection gate

Missing or incomplete privacy policies result in immediate rejection.

  • Host a policy covering collection, usage and storage, third-party sharing, retention, and contact. Live at travelanimator.com/privacy-policy, with a dedicated section for the MCP server and CLI — login, on-device storage, opt-in analytics, PostHog named as a US processor, and the never-collected list.
  • Rename the README heading to exactly ## Privacy Policy and link the HTTPS URL from it. Done.

One gap left: the policy states deletion on request and that saved routes persist until deleted, but names no retention period for analytics events. Add the window PostHog is configured for — retention is one of the five topics the requirements enumerate.

10

Tool annotations

Half fixed

1.0.2 introduced tada_render/mcp/tool_annotations.py; 1.0.3 corrected the read-only half. A live tools/list against the packed 1.1.0 bundle reports 38 tools, all titled, with 18 read-only hints and 5 destructive. The four credit tools added in 1.1.0 are annotated correctly, including openWorldHint.

Fixed in 1.0.3

await_render, get_render_result and estimate_render now declare readOnlyHint: true. This was the one that mattered most: await_render is called repeatedly through a render, and without the hint a ten-minute render was a stream of confirmation prompts on the product's primary flow.

Still declared non-destructive

Seven tools that modify existing data still report destructiveHint: false — create_route, update_point, update_animation_state, set_real_route, render_video, export_project, save_project_to_account.

Four are arguable. Three are harder to defend, because they touch data outside the project: render_video prunes all but the newest five renders, export_project overwrites a caller-chosen path, and save_project_to_account overwrites the account copy while dropping avatars, effects and animation settings. A false hint is an affirmative claim, not an omission — the criteria ask that annotations match actual behaviour, and these three suppress a prompt the user should see.

Not a blocker for submitting: every tool carries a title, and the auto-permission problem is gone. Worth folding into whatever ships next.

11

Prepare the reviewer's account

Provisioned

A dedicated review account exists, carrying credits and a fixed sign-in code so a reviewer can log in without reading the mailbox. That solves the real obstacle: login is by magic link, and a reviewer who cannot receive the email cannot exercise a single authenticated tool.

The gate is a balance, not a plan. Rendering costs one credit per video, charged when the render service prepares it, and a render fails with insufficient_credits at zero. Someone exercising 38 tools renders more than once, so leave enough on the account for several — one that runs dry mid-review reads as a broken product rather than an empty wallet. Confirm with get_credit_balance immediately before submitting, and again if review runs long.

It also wants saved routes, so list_account_routes and load_account_route return real data rather than empty arrays.

Where the credential goes

The submission form, and nowhere else. It asks for every link, credential and step, and it is a private channel to the review team. The address and code must not appear in this repo, the README, release notes, commit messages, this runbook, or a screenshot — a fixed code on a funded account is a standing credential, not a one-time token.

Two things to settle about that code: whether the fixed-code path is scoped to this one account or accepts a constant for any address, and when it gets revoked. Give it an end date at submission time rather than leaving it live indefinitely.

13

Wire it into the release pipeline

Not started

The existing publish-mcp-registry.yml already bumps server.json after a PyPI release. Extend that step to also rewrite mcpb/manifest.json’s version and mcpb/pyproject.toml’s pin, then mcpb pack and attach the result to the release.

Same reasoning as the existing guard: the bundle must never name a version that is not live on PyPI.

What the releases closed

Two package releases were cut for this submission, and between them they removed everything that lived in the code.

1.0.2 — annotations and login. Every tool gained a title. login, complete_login and logout became tools, so a Desktop user never opens a terminal — previously the one problem the uv server type could not solve, since MCPB installs with a double-click and a stdio server cannot prompt for credentials. That also made a user_config token field unnecessary rather than pending.

1.0.3 — read-only hints. await_render, get_render_result and estimate_render now declare themselves read-only, so they run without a confirmation prompt on every call. The render loop was the thing this mattered to.

What remains is outside the package entirely: the two policy answers in step 00, an analytics retention window in the privacy policy, a populated premium test account, the Desktop run-through, and the submission itself. Plus the seven destructive hints in step 10, which are worth fixing but block nothing.
